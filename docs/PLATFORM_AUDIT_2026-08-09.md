## 1. The #1 open decision: what is FORGE, actually?

Every one of the 8 domain research passes — independently, without coordinating with each other — surfaced the same unresolved conflict. That degree of convergence is itself the finding: this is not a niche documentation nit, it is the single fact that would change the shape of the next 6 months of roadmap work in every domain.

**The conflict, stated plainly:**

| Source | Framing |
|---|---|
| `.claude/rules/forge-youtube-replica.md` (live, always-applied Claude rule) | "Faithful YouTube replica." Parity preferred over invention. Divergent behavior should be **removed or refactored toward YouTube**, not extended as "FORGE-unique," unless the user explicitly asks. |
| `docs/FORGE_PROJECT_MASTER.md` §1 (executive summary) | "FORGE is a **skill-first creator platform**: on-demand lessons, live teaching, categories/skill tags, communities, and mock memberships." §8 (design-system section, ~line 198) also carries a stale cross-reference line — "familiar video IA, distinct visual identity (**not a YouTube clone**)" — attributed to `.cursor/rules/forge-frontend-ux.mdc`. **That rule file's current text has already moved on**: it now reads "YouTube-replica video platform... Prefer YouTube parity over skill-learning framing," aligned with `forge-youtube-replica.md`. So this is not a live third framing — just an orphaned line in §8 that should be corrected once §1 is rewritten. |
| `docs/CLIENT_OVERVIEW.md` | Mirrors the master doc's skill-first framing. |
| Root `FORGE_CREATOR_ECONOMY_OPERATING_SYSTEM_V3.0.md` | Explicitly frames FORGE as a "Creator Economy OS" — YouTube **+** Patreon **+** Discord/Circle **+** Skillshare/Coursera **+** Skool/Mighty Networks **+** Netflix/Disney+/Prime Video, combined. Self-describes (~line 707) as "an intentionally frozen blueprint snapshot... not updated as tasks complete," yet is linked from `docs/README.md` with no deprecated/historical marker, so it reads as live guidance. |
| `docs/phases/05-*` and `docs/phases/06-*` | Frame the user/creator platform in YouTube-parity terms. |

Three non-identical product statements are simultaneously "live" in the repo, and none references or reconciles with the other two. This is not just a docs inconsistency — it is architecturally load-bearing:

- `apps/api/src/common/features/skill-economy-lms.ts` ships an `isSkillEconomyLmsEnabled` flag, **default `false`**, with the code comment *"Default OFF for YouTube-replica mode."* Engineering has already, informally and partially, sided with the YouTube-replica framing at the code level — but this flag is undocumented in `FORGE_PROJECT_MASTER.md` §7's flags table and in `apps/api/.env.example`.
- Despite that flag, some "Creator Economy OS" surface still ships **unconditionally, unflagged**: the real-time Communities 2.0 stack (rooms/events/polls/groups/posts, 14-key community RBAC) and membership tiers. **Correction 2026-08-09:** an earlier pass of this audit additionally listed Channel Points, Mentorship, and Brands here — verified by direct code read to be incorrect. `ChannelPointsModule.register()`, and `BrandsController`/`MentorshipController`/`CommunityEngagementController` (conditionally registered in `communities.module.ts`), are already gated behind `isSkillEconomyLmsEnabled`/`SkillEconomyLmsGuard`, same as courses/cohorts/quizzes/certificates and the gamification/referral slices.
- A migration is literally named `YoutubeReplicaWave1`; `PublicUser`'s mapper adds YouTube-facing field aliases (`subscriberCount`, etc.) alongside the legacy `follow`-named ones; inline "// YouTube parity" comments exist in `users.controller.ts`.

So: the code is already leaning YouTube-replica-with-optional-extensions in some places, fully-merged-Creator-Economy-OS in others, and the docs don't reflect either state consistently.

### Where this conflict surfaces per domain

Every domain doc flags this same tension against its own surface area, without resolving it (by design — each doc explicitly declines to pick a side):

- **Product vision & data model** — three inconsistent vision statements; `Channel`-the-entity (Discord-style chat room) vs. `Channel`-the-concept (User's creator identity) naming collision compounds the confusion.
- **Upload/media pipeline** — `VideoType.PODCAST` with RSS-style fields, "paid events" ticketing shaped like webinar/cohort platforms, and after-live "discussion rooms" reusing `CommunityRoom` (no YouTube equivalent — YouTube's nearest analogue is the Community tab / live chat replay).
- **Discovery/search/recommendations** — `CoursesModule` has its own `courses/discover*` endpoints completely disconnected from unified `/search` and `/videos/feed/*`; courses are not searchable, recommendable, or part of up-next. The `Category`/`Subcategory`/`SkillTag` taxonomy is shaped and named for a "skills" framing even though it doubles as FORGE's video category system.
- **Engagement/social** — Communities module (rooms, events, polls, mentorship, groups, AI copilot, 14-key RBAC) is vastly larger than YouTube's actual Community tab (creator post + comment + one reaction); Courses/cohorts/quizzes/certificates/Channel Points have zero YouTube equivalent.
- **Creator monetization/analytics** — `FORGE_PROJECT_MASTER.md` calls memberships "mock" when in reality Stripe Connect destination charges are real; KPI docs present course-weighted engagement scores as default when they're flag-gated off by default; `CREATOR_DASHBOARD_WIREFRAMES.md` shows a "Course sales" revenue line with no backing implementation.
- **Moderation/safety/admin** — community moderation is Discord/Twitch-shaped (per-community roles, timed bans/mutes) vs. YouTube's actual model (comment holding, blocked lists, live-chat moderators, no member "roles"); `PHASE_07_ADMIN.md` explicitly keeps mentorship/channel-points admin tooling off primary nav "by design" — the admin IA is already hedging between the two framings instead of picking one.
- **Infra/scalability** — largely product-agnostic, but capacity planning can't be done meaningfully until scope is fixed: strict YouTube-replica implies planning for viral single-video spikes and live-concurrency; the current docs plan reactively against FORGE's own MAU targets instead.
- **Security/privacy/compliance** — `privacy.ts` describes only video-platform data categories with zero mention of course/quiz/certificate/mentorship data that exists elsewhere in the product's own tracker; RBAC gap-analysis is framed as "close the gap to YouTube's Manager/Editor/Viewer model" which presupposes an answer to the open question.

### Recommendation

Treat **YouTube's core model — channel (User), video, subscription (Follow), playlist, comment, live stream, Community tab — as the authoritative frame**, per the live `forge-youtube-replica.md` rule (it is an always-applied project rule, not a draft). Concretely:

1. **Keep** courses/cohorts/quizzes/certificates, mentorship, channel points, and the rich communities stack (rooms/events/polls/14-key RBAC) as **explicitly-labeled FORGE-specific extensions**, not baseline product. Courses, mentorship, channel points, and brands are already behind `isSkillEconomyLmsEnabled`/`SkillEconomyLmsGuard` (corrected 2026-08-09 — see §2.1 #2). What's still unconditional is the real-time Communities 2.0 stack (rooms/events/polls/groups/posts, 14-key RBAC) — extending the same flag pattern there is blocked on item 2 below, since posts/polls may be intended as FORGE's Community-tab equivalent (core), not an extension.
2. **Re-run `forge-youtube-replica.md`'s own test against each extension** — "remove or refactor toward YouTube, don't extend divergence as FORGE-unique, unless the user explicitly asks" — as an explicit, logged product decision per module (keep-as-extension / refactor-toward-YouTube / sunset), rather than leaving it as ambient, undocumented drift. This audit does not make that per-module call; it is a product decision that needs an owner (see open questions below).
3. **Rewrite `FORGE_PROJECT_MASTER.md` §1** to lead with the YouTube-parity frame (channel/video/subscription/live/community-tab) and describe the extension layer second, explicitly labeled optional/flagged — this audit makes a first, minimal step toward that (see [§5](#5-files-created-or-edited-by-this-audit)) without rewriting the rest of the file.
4. **Re-label or retire** the root `FORGE_CREATOR_ECONOMY_OPERATING_SYSTEM_V3.0.md` as historical/frozen in `docs/README.md` so it stops being read as current guidance, given it self-describes as a frozen blueprint snapshot.
5. Once the frame is fixed, redo capacity planning (infra), privacy-policy scope (security/compliance), and admin IA (moderation) against the now-unambiguous boundary — each of those domains explicitly said they couldn't complete their own recommendations without this decision first.

This is a recommendation, not a unilateral resolution — it is the natural reading of the one rule in the repo that is both explicit and currently enforced (`forge-youtube-replica.md` is in the "Always Apply" rule set), applied consistently, while preserving already-built product investment as an intentional, documented layer rather than deleting it.

**Decision: accepted, 2026-08-09.** Executed so far: `FORGE_PROJECT_MASTER.md` §1 rewritten to lead with the YouTube-parity frame (channel/video/subscription/live/community-tab) with the extension layer described second; §7 flags table now documents `FEATURES_SKILL_ECONOMY_LMS`; §8's orphaned "not a YouTube clone" line corrected; root `FORGE_CREATOR_ECONOMY_OPERATING_SYSTEM_V3.0.md` relabeled historical/frozen in `docs/README.md`. **Correction, same day:** direct code verification found Channel Points/Mentorship/Brands already gated (item 1 above is largely done, not open).

**Item 2 (per-module keep/refactor/sunset test), closed 2026-08-12:**
- **Courses/cohorts/quizzes/certificates, mentorship, channel points, brands — sunset, already executed at the frontend.** A read-only sweep of `apps/web`/`apps/mobile` for these features found **zero remaining UI** — no pages, components, nav links, or screens. `apps/mobile/lib/core/router/app_router.dart` hardcodes redirects for every legacy deep link to its YouTube-parity destination (e.g. `/studio/channel-points` → `/studio`, `/studio/courses` → `/studio/videos`), with an explicit in-code comment: *"Skill-economy LMS soft-retire — keep deep links from crashing."* `apps/admin/src/app/{channel-points,mentorship}` are stub redirects to `/dashboard`. Git history (`docs/phases/DEPTH_BACKLOG.md`, commits `3b328d6`/`b5d6653`/`84bc613`/`a925947`/`836a3bb`/`95d50c3`) confirms this was a deliberate, already-completed removal, not an oversight. Backend stays defensively flag-gated off (`FEATURES_SKILL_ECONOMY_LMS=false`) rather than deleted — no code change needed; the module-level decision was already made and is now just documented (`FORGE_PROJECT_MASTER.md` §1/§7). One asymmetry worth flagging: flipping the backend flag back to `true` would **not** resurrect any frontend UI (there's no client-side flag mirroring it — the removal was static, not conditional) — documented so a future "let's re-enable this" attempt doesn't get surprised.
- **Communities 2.0 (rooms/events/polls/groups/posts, 14-key permission matrix) — split, not a single verdict.** Posts + polls + membership tiers are **core**: this is FORGE's actual implementation of YouTube's Community tab (text/image posts, polls) and Channel Memberships — no divergence to resolve, ships unconditionally, correctly. Rooms (real-time chat) and events/RSVPs have no YouTube Community-tab equivalent and are a genuine, labeled **extension** — but unlike the LMS surfaces above, they're unconditionally wired into live web/mobile UI today and load-bearing for moderation/permissions/analytics work already shipped this session (#4, #5, #6, #7, #9, #18 all build on the community-role system rooms/events also use). Sunsetting or flag-gating them now would be a breaking product change to live functionality, disproportionate to what a documentation exercise should trigger on its own authority — `forge-core.md`'s "smallest change" and `forge-ship.md`'s "no unrequested disruption" both cut against it. Decision: **keep, label as extension in `FORGE_PROJECT_MASTER.md`, do not flag-gate** — a future decision to actually disable rooms/events needs its own explicit ask, this closes only the labeling question.

Deliberately does **not** auto-action anything: an unverified user report auto-blocking content (unlike the community pipeline's LLM-judge-score-driven auto-actions) would be a mass-reporting abuse vector, so this only reorders the admin triage queue (P0 first).

**Not done, explicitly not resolved:** the two systems remain organizationally separate — different tables (`reports` vs `community_reports`), different admin surfaces, no cross-linking between a platform report and a community report about related content. A real "bridge" (unified inbox, shared resolution workflow) is a bigger structural change touching the admin web app, not attempted here. Watch screen's own video-report entry point (`_ReportVideoButton` in `watch_screen.dart`) still free-text with no preset picker at all — inconsistent with every other report flow, not upgraded in this pass.

### 2.3 Trust & safety / moderation

- No copyright/DMCA notice-and-counter-notice pipeline, despite "Copyright infringement" being a selectable report reason in the UI. No designated-agent contact in `docs/LEGAL.md`.
  - **Fixed 2026-08-12:** built the actual §512 notice-and-takedown + counter-notice mechanics (`CopyrightModule` — entities, service, controller, hourly auto-reinstatement worker). A valid notice disables the video and issues a copyright strike immediately (no human-review step — that mirrors the statute, a valid notice *is* the trigger). A valid counter-notice schedules auto-reinstatement after the 10-business-day window unless an admin rejects it (e.g. litigation reported). Full writeup: [COPYRIGHT_DMCA.md](./COPYRIGHT_DMCA.md). **Still genuinely missing, not fixed:** designated-agent registration with the U.S. Copyright Office — a real filing outside any codebase, required before this can support actual DMCA safe-harbor reliance. 24 new tests (service + worker + business-day math), typecheck clean, full API suite 1201/1201 green.
- No account-level strike/warning ladder — enforcement is a binary `isActive` disable only; no escalation state machine, no appeals mechanism anywhere in the codebase (zero matches for "appeal" or "strike" across all 4 apps).
  - **Fixed 2026-08-12:** `AccountStrikesModule` — ladder mirrors YouTube's own published numbers (1st = warning, 2nd within 90 days = 2-week upload/live restriction, 3rd = termination *recommended*, never auto-executed — matches `ESCALATION_RULES.md` §3's "irreversible account actions are admin-only"). Upload restriction is actually enforced (`UploadNotRestrictedGuard` on video-upload and stream-start). Self-service appeal (`POST /account-strikes/:id/appeal`) + admin resolution (`PATCH /admin/strikes/:strikeId/appeal`) — granting lifts any restriction. 11 new tests.
- Video moderation is 100% reactive/manual (single `moderationStatus` enum set by admin PATCH after the fact) — no automated pre-publish scan, unlike the AI-judge pipeline already built for community text.
- No admin/privileged-action audit log table (only a narrower creator-scoped audit log).
- No rate-limiting or trust-weighting on report-creation endpoints — mass-reporting/review-bombing is unmitigated. **Fixed 2026-08-09:** added `@Throttle({ limit: 10, ttl: 60_000 })` to `POST /reports` and `POST /communities/:communityId/reports` (matches the existing per-route throttle pattern in `auth.controller.ts`). Trust-weighting (lower limits for low-trust accounts) still open.
- No distinct trust-and-safety "moderator" role between community moderators and full platform `ADMIN` — all-or-nothing at platform scope (independently flagged by both moderation and security domains).
- `docs/ESCALATION_RULES.md` reads as platform-wide but every rule it cites is actually community/chat-scoped only — it doesn't cover video reports, copyright, account strikes, or admin-wide enforcement despite being the repo's only "escalation rules" doc.

### 2.4 Security / privacy / compliance

- **No MFA/2FA anywhere** in the codebase (password + Redis-backed lockout only) — significant gap for a platform with creator payouts and admin accounts.
  - **Fixed 2026-08-11 (opt-in TOTP, first slice):** self-service enroll/verify/disable (`POST /auth/mfa/enroll`, `POST /auth/mfa/verify`, `DELETE /auth/mfa`) plus a login-time challenge (`POST /auth/mfa/login-verify`) for accounts that turn it on. TOTP secret stored AES-256-GCM encrypted (`common/utils/encryption.util.ts`, key via `MFA_ENCRYPTION_KEY`, not yet required in prod schema since the feature is opt-in); 10 single-use bcrypt-hashed backup codes issued on enrollment; login-code verification is rate-limited (5 attempts / 10 min) via Redis, matching the existing `AuthEmailOtpService` pattern. Uses `otplib` v12 (`authenticator` API) — **not v13**, whose default build pulls in ESM-only transitive deps (`@scure/base`) that this repo's Jest config can't transform; caught during test-writing, not assumed. New migration `2040000000000-user-mfa-columns.ts`. **Update 2026-08-16:** the Google-OAuth MFA bypass flagged below is fixed — `loginWithGoogle` now checks `user.mfaEnabled` and returns the same `{ mfaRequired, challengeToken }` shape as password login (`auth.service.ts`, covered by `AuthService`'s `loginWithGoogle with MFA enabled` spec). **Still not covered by this pass:** mandatory MFA for admin/high-payout creators (still opt-in); backup-code low-count warning/regeneration UX. Typecheck clean; 26 new tests across `encryption.util` (6), `AuthMfaService` (11), `AuthService`'s new login/`completeMfaLogin` cases (4), and the new `AuthController` MFA spec (5), all green — full API suite regression run in progress at time of writing.
- No self-service account deletion (no `DELETE` route in `users.controller.ts`) and no data-export/portability endpoint; only path is admin-triggered `AdminService.deleteUser`.
  - **Fixed 2026-08-09:** `deleteUser` now hides the deleted user's videos (visibility → `PRIVATE`, cache busted, `video.updated` emitted) and ends any active/idle streams via the existing `StreamingService.endStream`.
  - **Fixed 2026-08-12 (owned-community transfer):** `deleteUser` now promotes the longest-standing `OWNER`-tier delegate on each community the deleted user created, falling back to the longest-standing `ADMIN`-tier delegate if no `OWNER` exists; emits `community.ownership_transferred`. **Still open, explicitly not resolved:** when *no* delegate of either tier exists, the community is left as-is (`creatorId` still points at the anonymized, logged-out user) — safe (no crash, no access change) but not a full fix; that case has no delegate to promote, and inventing a new archival lifecycle for ownerless communities is a bigger design question than this fix scoped in. 3 new tests, admin/users/communities suites (221 tests) green.
  - **Fixed 2026-08-11:** added `DELETE /users/me` (password-confirmed, reuses `AdminService.deleteUser`'s content-cleanup) and `GET /users/me/export` (profile + owned videos + watch history + playlists). `UsersModule` now imports `AdminModule` via `forwardRef` (mirrors the existing `ContentModule` forwardRef in the same file) so the self-service route can call the same tested deletion path instead of duplicating it. Typecheck clean, 232 tests green across users/admin/content/streaming. **Not verified:** a real app boot (`npm run start:dev` against a live DB) — no Docker/Postgres available in this environment to confirm the new circular module import resolves correctly at runtime; do this once before merge. **Known gap:** password confirmation blocks Google-OAuth-only accounts (they get a random unusable password at signup) — they'd need a "set password" step first; not fixed here, no DSAR intake for comments/community posts/analytics events either (documented, not silently dropped).
- No DSAR/privacy-request intake beyond a support mailto address; no cookie-consent banner despite `privacy.ts` describing cookie usage in GDPR-relevant terms.
- No per-channel delegated access (YouTube's Manager/Editor/Viewer via Brand Accounts) — one owner per channel, no collaborator model.
- Mobile app has **zero accessibility implementation** (no `Semantics`/a11y code anywhere in `apps/mobile/lib`), and this gap isn't even acknowledged as deferred in `PHASE_21_A11Y.md` (which scopes itself to web only and reports ~70% complete, implicitly overstating platform-wide a11y maturity) — unlike every other tracked gap in that doc.
  - **Nuance found 2026-08-11:** "zero" was accurate for explicit `Semantics()`/`semanticLabel` usage (confirmed: zero matches), but coverage was already uneven, not uniformly zero — `watch_screen.dart`'s primary like/dislike/share row already had `tooltip:` on every `IconButton.filledTonal` (which Flutter uses as the accessible label automatically), while `feed_screen.dart`'s `_ActionButton` and `shorts_screen.dart`'s `_ShortAction` (custom `GestureDetector`/`InkWell` widgets, the like/comment/share buttons on the two highest-traffic screens) had **no accessible label at all** — a screen reader landing on them announced nothing meaningful.
  - **Fixed 2026-08-11 (bounded first slice, not full-app coverage):** added `Semantics(button: true, label: ..., excludeSemantics: true)` to `_ActionButton` (feed) and `_ShortAction` (shorts), with dynamic labels ("Like, 42 likes" / "Unlike, 43 likes" / "Comment, N comments" / "Share"). Added missing `tooltip:` to bare `IconButton`s on the three highest-traffic screens (feed app bar refresh/search; shorts back/post-comment/comment-like/dislike/reply; watch back/post-comment/comment-like/reply). 1 new semantics regression test (`feed_screen_test.dart`, using `tester.getSemantics`/`matchesSemantics`) establishes the testable pattern for future screens. `dart analyze` clean; feed/shorts/watch widget suites (37 tests) all green.
  - **Explicitly not done, not silently dropped:** this covers 3 of the highest-traffic screens. A `grep` count found `IconButton(` in 37 files across the app; the other ~34 (studio/creator screens, profile, playlists, live, community, settings sub-pages, etc.) are unaudited. No color-contrast audit, no focus-order/traversal review, no `flutter_test` `meetsGuideline` checks (tap-target size, text contrast) added, no manual screen-reader (VoiceOver/TalkBack) pass performed. Full-app coverage is its own multi-day pass, not attempted here — see backlog.
- No step-up auth beyond admin-role escalation — account deletion, recovery-email changes, and impersonation-token issuance have no equivalent friction.

### 2.5 Discovery / search / recommendations

- No transcript/caption search — FTS only indexes title/description/tag/category, despite caption infrastructure already existing.
  - **Fixed 2026-08-11:** primary caption track fetched (reusing the existing SSRF-safe fetch path in `videos.service.ts`), parsed to plain text (`webvtt.util.ts`, no new dependency), stored in `videos.caption_text`, folded into `search_vector` at weight D. Set best-effort on `setCaptionUrl` — never blocks the write on fetch failure. 10 new tests (parser + indexing behavior). **Not done:** multi-language indexing (only the primary track), backfill for already-captioned videos (only applies going forward from a `setCaptionUrl` call).
- No session-based ("this sitting") personalization signal; no exploration budget in `forYou` ranking (cold-start problem for creators, not just viewers). **Still open** — this needs a ranking-algorithm design decision (what counts as a "session," what exploration rate), not a mechanical fix; not attempted here.
- Playlist search has zero ranking (`ILIKE` + `updatedAt DESC` only).
  - **Fixed 2026-08-11:** added a real `search_vector` generated column (migration `2060000000000-playlist-search-vector.ts`) and rewrote playlist search to rank by `ts_rank_cd`, with the same ILIKE-fallback resilience pattern used for video/user search. 2 new/updated tests.
- **Two Phase docs are stale relative to `main`**: `PHASE_11_SEARCH.md` and `PHASE_12_RECS.md` both list already-shipped features as "Deferred" (playlist search + duration/date filters; diversity re-ranking, Shorts ranking, "not interested" feedback loop) — completion percentages (85%, 60%) likely understate actual state.

### 2.6 Upload / media / live

- No malware/CSAM/policy content scanning, no duplicate/fingerprint (Content-ID-style) detection on upload.
  - **Fixed (scaffolding) 2026-08-12:** added a pluggable `ContentScanService` (`apps/api/src/modules/content/content-scan/`) called from both video-ready paths (`MuxVodService.handleAssetReady`, `VideoProcessorWorker.process`) right before a video is marked `READY`. Default provider (`none`) approves everything — identical to prior behavior. A `webhook` provider is available for a generic REST scan integration; it fails closed to `hold` (not open) on any error/timeout/unrecognized response, since a safety scan should err toward caution. A non-`approve` verdict sets `Video.moderationStatus` (`held`/`blocked`), which the existing `shouldIndexVideo()` gate already uses to keep `indexedAt` null — so a flagged video never reaches feed/search/recommendations — and emits `video.content_scan_held` instead of `video.ready` so subscriber/feed notifications don't fire for unreviewed content. **No real vendor is integrated** — Google CSAI Match / Thorn Safer / Microsoft PhotoDNA all require legal agreements and credentials outside this codebase; see `docs/CONTENT_SCANNING.md`. Duplicate/fingerprint (Content-ID-style) detection remains entirely unaddressed — out of scope for this pass. 10 new tests (service + both providers), typecheck clean, content/workers suites (176 tests) green.
- FFmpeg self-hosted transcode path is serial (BullMQ concurrency:1) and all-or-nothing (blocks READY until all 4 HLS renditions finish) — a real scalability limitation understated in `docs/MEDIA.md` as a mere config choice vs. Mux's async webhook path.
- `scheduledPublishAt` only gates discovery via query-time filtering — no scheduler/cron actually fires a "published" event/notification at the scheduled moment.
  - **Fixed 2026-08-12 — this was worse than "just missing a notification."** `indexedAt` (required by `applyDiscoverableVideoFilters`'s `indexed_at IS NOT NULL` gate — the actual feed/search visibility filter) is set once at transcode-ready time based on whether the schedule had *already* passed; nothing ever revisited it afterward. A video scheduled for the future stayed **permanently un-indexed** (invisible in feed/search forever) once ready, unless a creator happened to edit it again after the scheduled time. Confirmed this had already bitten the codebase once — `1740000000002-backfill-video-indexed-at.ts` is a one-time manual SQL repair for exactly this, with no recurring fix, so any video scheduled after that migration ran would hit the same bug again. Root-caused and fixed with a real recurring mechanism: `ScheduledPublishService.runScheduledPublish()` + a 1-minute BullMQ repeatable job (`ScheduledPublishScheduler`/`ScheduledPublishWorker`, mirroring the existing `AnalyticsRetentionService`/`Worker` pattern) that indexes any due video, busts its cache, and emits `video.published`. New partial index (`2080000000000-scheduled-publish-index.ts`) backs the scan. 5 new tests (service + worker), typecheck clean, content/workers suites (164 tests) green.
- Highlight clip export to Mux is schema/API-ready but the job itself doesn't exist ("TBD" per `docs/LIVE.md`'s own deferred list).
- Only English auto-captions requested at Mux ingest time (hardcoded `language_code: 'en'`) though the schema supports multi-language.
- `docs/SCALE_LIVE.md`'s 100K-viewer design is unimplemented and not cross-linked from `docs/LIVE.md`'s capabilities table (shipped ceiling: ~10K viewers/stream) — risk of a reader conflating proposal with current capability.

### 2.7 Engagement / social

- No comment spam/toxicity gate or held-for-review queue on video comments (exists for community posts, not video comments).
  - **Fixed 2026-08-13 (gate only, not the full three-layer stack):** wired the same regex fast-path used for community posts (`AiModerationService.scoreSpam`, `apps/api/src/modules/communities/ai-moderation.service.ts`) into `EngagementService.createComment` — a flagged comment throws `ForbiddenException('Comment blocked by automated moderation')` before persistence, matching `community-posts.service.ts`'s exact behavior/message. **Not ported:** the async OpenAI-moderation + LLM-judge tail and the auto-spam-report path — those write into `CommunityReport`, which is community-scoped (`communityId` required) and not a clean fit for video comments; building a matching held-for-review admin surface for engagement content is its own scoped follow-up, not attempted here. 2 new tests (`engagement.service.spec.ts`), full engagement suite green.
- No server-side `Share` entity/endpoint — shares are entirely untracked.
  - **Fixed 2026-08-11:** new `Share` entity (`shares` table, migration `2070000000000-video-shares.ts`) + `videos.share_count` counter. `POST /videos/:id/share` (public, optional-auth so logged-out shares count too, throttled 30/min) in `EngagementController`/`EngagementService.recordShare`. Wired to every video-share call site found: web `VideoInfo.tsx` (native share, copy-link, embed-copy) and mobile `feed_screen.dart`/`shorts_screen.dart` (native share + copy-link). **Not wired:** mobile `profile_screen.dart` (channel share) and `live_watch_screen.dart` (stream share) — different resource types, out of scope for this endpoint. 4 new backend tests, typecheck clean on web/mobile, existing feed/shorts widget tests (19) still green.
- `email-digest.service.ts`/`email-digest.scheduler.ts` already implement a real daily BullMQ cron digest job, but `packages/shared-types/src/notification-preferences.ts` still comments it as "reserved — no digest job sends yet" (stale code comment, not just a doc issue). **Fixed 2026-08-09** — comment corrected in the initial audit pass.
- Push preference matrix UI is missing on frontend even though backend category-mute infrastructure is already built and more complete than `PHASE_15_COMMUNICATION.md` credits.
  - **Corrected 2026-08-11:** only half true. **Web already had it**, fully wired (`components/settings/NotificationPreferencesSettings.tsx`, rendered in `app/profile/settings/page.tsx`) — the earlier audit pass didn't check before writing this finding. **Mobile genuinely had nothing** — added `_NotificationPreferencesSection` to `profile_settings_screen.dart` + `WatchRepository.getNotificationPreferences`/`setNotificationPreferences`, mirroring the web component against the same endpoint. 2 new repository tests, `dart analyze` clean.
- `FollowNotifyLevel.PERSONALIZED` exists in schema/UI but has no distinct ranking behavior behind it — a labeled-but-inert setting. **Still open** — fixing this for real means wiring follow-level into notification dispatch against an affinity/interest signal; not attempted here, scoped out to keep this pass bounded rather than silently dropped.
- Deleted-parent-comment thread semantics unverified (`parentId onDelete: SET NULL` may orphan replies instead of a YouTube-style tombstone).

### 2.8 Creator monetization / analytics

- **No ad revenue model at all** — no `AdsModule`, no ad-break/impression entities, no RPM/CPM — despite ads being YouTube's primary monetization stream. **Still true 2026-08-13, by design — flagged as a business decision, not implemented speculatively.** Real ad-serving needs a chosen ad network (AdSense/AdMob/programmatic), ad formats (pre-roll/mid-roll/display, skippable or not), and a revenue-share percentage — none of which this codebase can decide on its own. See `docs/MONETIZATION.md` §4.
- No graduated monetization-eligibility gate (YouTube-style subscriber/watch-hour thresholds) — any creator passing the general approval guard can immediately monetize; no distinct "monetization eligibility" concept separate from `creatorStatus` exists anywhere (independently flagged by product-vision domain too).
  - **Fixed 2026-08-13:** `MonetizationEligibilityService` (`GET creators/me/monetization/eligibility`) checks YouTube Partner Program's own published thresholds — 1,000 subscribers AND (4,000 watch hours/12mo OR 10M Shorts views/90d), approved creator status, no active strike restriction. Read-only — doesn't unlock anything yet since there's no live ad revenue for it to gate. 6 new tests. See `docs/MONETIZATION.md` §5.
- No unified creator payout ledger — MRR, Super Thanks, and (future) ad revenue are three separate surfaces with nothing joining them into "what lands in my bank account."
  - **Fixed 2026-08-13:** `CreatorEarningsService` (`GET creators/me/earnings` + CSV export) rolls subscriptions + Super Thanks + Super Chat into one summary. **Also found and fixed a real bug while building this**: Super Chat's production checkout path had no Stripe Connect wiring at all — every live tip went entirely to the platform's Stripe account with zero payout mechanism to the creator (Super Thanks and subscriptions both use Connect destination charges; Super Chat was missing it). Fixed to match: `createSuperChatCheckout` now requires Connect onboarding same as Super Thanks, `StreamMessage` gained fee-split columns (migration `2110000000000-super-chat-fee-split.ts`). 5 new/updated tests (billing + stream-chat). See `docs/MONETIZATION.md` §2. Ad revenue itself is intentionally excluded from the ledger (hardcoded `0`, not faked) — see the ad-revenue bullet above.
- Unverified whether Stripe refund/dispute webhooks (`charge.refunded`, `charge.dispute.created`) correctly reverse creator net earnings — flagged as needing a dedicated check, not confirmed broken.
- **Two same-phase docs directly contradict each other**: `PHASE_14_MONETIZATION.md` lists Super Thanks-for-VOD as Deferred; `PHASE_14_REPORT.md` correctly says it's shipped and verified. It is, in fact, fully implemented.
- `FORGE_PROJECT_MASTER.md` calls memberships "mock" — actually real Stripe Connect destination charges with platform-fee calc, dunning, device-capped access sessions; "mock" only accurately describes the `BILLING_PROVIDER=stub` dev fallback.

### 2.9 Infra / scalability / reliability

- Single-region deployment (Fly `bom` only), no documented failover procedure for a full-region outage.
  - **Addressed 2026-08-11 (design, not infra change):** wrote [SCALE_MULTI_REGION.md](./SCALE_MULTI_REGION.md) — current single-region state, a sequenced proposal (worker HA → 2nd Fly region → Neon read replica → Redis cluster → full failover runbook), and an explicit list of what it deliberately doesn't decide (which region, RTO/RPO, cost) since those are product/ops calls. No actual infra was provisioned — this is a plan, matching the existing `SCALE_LIVE.md` "proposed, not implemented" convention.
- No cache-stampede protection (jittered TTL / single-flight) on hot Redis keys — thundering-herd risk on viral content.
  - **Fixed 2026-08-11:** new `common/redis/cache-stampede.util.ts` (`singleFlight` request coalescing + `jitterTtl`), wired into the two hottest read-through caches: video detail (`videos.service.ts findById`) and search (`search.service.ts`). A cache-miss burst now shares one DB query per instance instead of N, and TTLs no longer expire in lockstep. 7 new tests for the util; content/search suites (152 tests) still green.
- No distributed tracing in production; no continuous synthetic/canary monitoring of critical journeys.
  - **Corrected 2026-08-11 (tracing):** this was wrong — distributed tracing is already fully built and wired (`src/instrument.ts` → `otel-bootstrap.ts`, OpenTelemetry SDK + OTLP exporter + HTTP/Nest/Postgres instrumentation, imported first-line in `main.ts`), and already documented in `docs/OBSERVABILITY.md` and `.env.example`. It only *activates* when `OTEL_EXPORTER_OTLP_ENDPOINT` is set — that's an ops decision (pointing it at a Tempo/Jaeger/Datadog collector), not a missing capability. The earlier audit pass didn't check before writing this finding.
  - **Fixed 2026-08-11 (synthetic monitoring):** this part was real — `scripts/smoke-api.sh` existed but only ran manually/at deploy. Added `.github/workflows/synthetic-monitoring.yml`, a scheduled (every 15 min) GitHub Actions job running the existing public-mode smoke script (`FORGE_SMOKE_MODE=public` — read-only GETs, no secrets, no auth) against production, so an outage between deploys gets caught. Only takes effect once merged to `main` (schedule triggers read from the default branch).
- Worker tier is a single machine (`--ha=false`) — an accepted but real SPOF for all background job processing. **Still open** — flagged as sequencing step 1 in `SCALE_MULTI_REGION.md`, not fixed here (changing Fly machine count/HA is a live infra change, not something to flip unilaterally outside a deploy window).
- Two thin phase docs (`PHASE_18_INFRA.md`, `PHASE_19_PERFORMANCE.md`, "Status: Documented/Verified" one-liners) badly undersell the far more detailed and current picture in `docs/operations/*` and `docs/audits/*` — a reader of only the phase docs would miss single-region risk, worker SPOF, and a 2026-07-26 finding of no GitHub branch protection on `main` plus an Actions workflow pinned to `@master` alongside static, unrotated AWS IAM keys in privileged deploy jobs (unverified as of this audit — needs a live re-check, not re-confirmed here).

## 6. Zero-trust re-audit & fixes, 2026-08-13

A second, independent zero-trust re-audit (9 parallel domain passes, treating this doc and every other prior audit as leads only, not ground truth) found 4 real P0-severity bugs and a further batch of P1 gaps, then fixed the P0s same-day:

**P0 fixed:**
- `mux-vod.service.ts` hardcoded `playback_policy: ['public']` for every video regardless of `visibility` — signed-URL code for paid/gated video was signing against an asset that was never actually created `signed`, so it did nothing. Fixed: policy now derives from visibility at ingest, plus a new `syncPlaybackPolicy()` that re-issues the playback id when visibility changes post-publish.
- `loginWithGoogle` skipped the MFA challenge entirely — any MFA-enrolled account with a linked Google login could bypass TOTP via `GET /auth/google/callback`. Fixed to mirror the password-login MFA branch.
- Super Chat/Super Thanks checkout never set `payment_intent_data.metadata`, so `charge.refunded` couldn't identify tip charges at all (they fell through to the generic subscription-refund branch, silently mis-tagged). No `charge.dispute.created` handling existed anywhere. Fixed: metadata added, dispute handling added, refunded/disputed tips now excluded from creator earnings totals (migration `2120000000000-tip-refund-tracking`).
- `/studio/community` — a live, linked Studio Community page — was in the `next.config.mjs` orphan-redirect list left over from the skill-economy-LMS cleanup, silently bouncing every visit back to `/studio`. Removed.

**P1 fixed same session:** video comment moderation (held-for-review instead of hard-reject, `migration 2130000000000`), admin audit log for privileged actions (`migration 2140000000000`), Google-OAuth-only account self-deletion (was structurally impossible — no usable password to confirm with), mobile raw `Dio()` bypass in `channel_community_panel.dart`, Playwright a11y-smoke direct-request-to-prod tests now gated like `checkout.spec.ts`.

**Still open, flagged as needing a decision rather than guessed at:** category taxonomy is skill/craft-shaped and every video is forced through it — a product-shape decision, not a bug fix. CSAM/pre-publish scanning is fully no-op (`NoopContentScanProvider`) with no real vendor — needs vendor selection/contract, not engineering. AWS OIDC migration's **app-side code was already done 2026-08-13** (`create-s3-client.ts` supports `AWS_ROLE_ARN`-gated Fly-OIDC→STS federation, defaulting to today's static keys when unset — see `docs/operations/AWS_CREDENTIAL_ROTATION.md`) — this section previously said it wasn't built yet, which was stale even at the time this correction pass ran. What's genuinely still open is the one-time AWS-side IAM setup (OIDC identity provider + role), which needs real AWS console/CLI access this repo/agent doesn't have; ready-to-apply trust/permission policy JSON now lives at `docs/operations/aws-oidc/`.

**Resolved 2026-08-14 (PR #195), delta-verified 2026-08-16:** MFA now has a real frontend on both clients — `apps/web/src/components/settings/MfaSettings.tsx` (wired into `profile/settings`) and `apps/mobile/lib/features/auth/presentation/mfa_challenge_screen.dart` — closing the "backend-only" gap noted above. The copyright/strikes admin UI also shipped — `apps/admin/src/app/copyright/page.tsx` (477 lines, in `AdminShell.tsx` nav). Both were previously listed as open in this section; `docs/YOUTUBE_PARITY_ROADMAP.md`'s MVP-3 table has been corrected to match (most of that table was stale for the same reason — see its 2026-08-16 delta-audit note).
